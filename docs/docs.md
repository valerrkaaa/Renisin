# vterminal — документация проекта

## 1. Назначение

`vterminal` — Windows-приложение для отправки команд в командную оболочку
и просмотра результатов в формате чата. Поддерживает несколько открытых
CMD-сессий одновременно, каждую со своим зашифрованным журналом.

Цель архитектуры — позволить добавлять новые драйверы (SSH, PowerShell и т.п.),
новые способы хранения и новые элементы UI без переписывания основной логики.

Сессия типа LLM добавляет к терминалу чат одной сохранённой модели LM Studio.


## 2. Текущий статус

Реализованы локальные CMD-сессии и SSH-сессии, зашифрованный журнал
и несколько параллельных сессий.

### 2.1. Реализовано

- Локальные CMD-сессии от имени текущего пользователя Windows.
- Несколько сессий одновременно. Команды в разных сессиях выполняются
  параллельно, внутри одной сессии — последовательно.
- Список сессий в левой панели: `▶` — текущая, `●` — открытая,
  `○` — закрытая. Подпись «активна», «активна · выполняется»,
  «не активна» или «не активна · ошибка». Удаление с подтверждением.
- Создание сессии: имя, пароль журнала, подтверждение.
- Открытие закрытой сессии: разблокировка журнала по паролю.
- Закрытие активной сессии; журнал остаётся зашифрованным на диске.
- Чат-подобная история с разным оформлением команды, stdout, stderr,
  системных сообщений, ошибок и кода возврата.
- Отслеживание рабочей директории между командами (`cd`, `cd ..`,
  `cd /d D:\...`).
- Отдельное отображение ошибки запуска процесса и ошибки самой команды.
- Копирование команды и вывода. Up/Down подставляют команды, которые
  сейчас видны в ленте этой сессии. Черновик строки запоминается
  отдельно для каждой сессии.
- Перед полем ввода кнопки «Вставить» и «Вставить и выполнить».
  Подсказка появляется при наведении и может быть в несколько строк.
  Поле команды многострочное: Enter отправляет законченную команду,
  а внутри незакрытого heredoc, кавычек или после `\` добавляет строку.
  Shift+Enter всегда добавляет строку. Вставка сохраняет переносы.
- Текст ответа модели выделяется мышью. В живом экране, в том числе
  в `nano`, протягивание мыши выделяет ячейки и копирует их.
- Tab в поле ввода дополняет строку. Если вариантов несколько, под полем
  подсказка, второй Tab показывает список. Список в журнал не пишется.
- Каждая команда выполняется в PTY: пока процесс жив, клавиши уходят
  в блок ответа (`nano`, `less`, Ctrl+C). После выхода фокус возвращается
  в нижнее поле. Живые кадры экрана в журнал не пишутся; в журнал попадает
  текст основного экрана без alternate screen. Высота PTY берётся
  из видимой ленты. После выхода экран остаётся, клавиатура выключается.
  Клавиши F1–F12 уходят в процесс. Цвет на экране — тот, что вывел
  терминал; у PTY нет отдельного stderr.
- Зашифрованный журнал: дозапись в конец файла, AES-GCM на запись,
  ключ из пароля через PBKDF2-HMAC-SHA256, проверка целостности
  при разблокировке.
- Каталог сессий в JSON без секретов.
- Ошибка записи журнала показывается пользователю и не скрывается.
  Номер следующей записи увеличивается только после успешной дозаписи.
- SSH: пароль или ключ, проверка ключа хоста, PTY на каждую команду.
  Команды с `sudo` идут на один и тот же удалённый экран, пока соединение
  живо. Пароль читает сам `sudo` и помнит его своим билетом; клиент пароль
  не сохраняет и не кладёт во временный файл. Сколько его не спрашивать
  снова, решает удалённая ОС (`timestamp_timeout`). Новое подключение
  или закрытый экран спрашивают пароль заново.
  Если хост недоступен, журнал всё равно открывается. Над историей
  плашка «Сессия недоступна» и кнопка восстановления соединения.
- Профили моделей (OpenAI, LM Studio, OpenRouter) в
  `%APPDATA%\vibe_terminal\llm_profiles.json`. Вид API хранится в профиле.
  Новая модель по умолчанию — OpenAI. Запись без поля `api_kind`
  читается как LM Studio. Перед сохранением сервис запрашивает
  `GET /v1/models`. Ключ обязателен для OpenAI и OpenRouter.
  В каталоге сессии хранится только id профиля, без ключа.
- Сессия с моделью делит правую область: слева терминал CMD или SSH,
  справа чат. В запрос к модели уходит только переписка этой сессии.
  Кнопка `>` у команды дописывает команду и вывод в поле чата,
  оборачивая их в блок. В ответе модели блоки ```bash дают кнопки
  «Выполнить» и «Вставить». Пока модель отвечает, в чате видна
  анимация «Думает».   В запрос добавляется системная просьба давать
  по одной команде в блоке. Замену в файле модель описывает блоком
  ```edit``` с `OLD` и `NEW`. Сервис меняет файл только если старый
  фрагмент найден ровно один раз, остальные байты не переписывает.   После ответа начало сообщения
  поднимается к верхней границе чата. Над чатом виден примерный
  размер контекста. «Сбросить» оставляет сообщения на экране, но
  модель их больше не получает. Удаление незавершённой
  команды останавливает её процесс и снова открывает поле ввода.
- Обрыв терминала и обрыв модели независимы: плашка и повторная
  проверка стоят только над своей колонкой.

### 2.2. Не реализовано

- Повышение прав CMD (`windows_elevation.py`).


## 3. Архитектура

Принцип: однонаправленные зависимости и чистая архитектура.

    ui/  ────────→ application/ ────────→ domain.py
                       ↑                    ↑
                       │                    │
    drivers/ ──────────┘                    │
    storage/ ──────────┴────────────────────┘
    screen_log.py  ←  drivers/, ui/terminal_view.py

`screen_log.py` — лист без Qt и без процессов. Его импортируют драйверы
и виджет терминала. UI по-прежнему не импортирует `drivers/` и `storage/`.

    main.py → ui/, application/, drivers/, storage/, domain.py

`main.py` — единственное место, где создаются конкретные реализации
и связываются зависимости.

Правила:

- UI не запускает процессы и не читает/не пишет файлы журналов,
  не занимается шифрованием.
- Сценарии приложения не зависят от PySide6, subprocess, SSH-библиотек,
  криптографии и конкретных реализаций хранилищ.
- Драйверы и хранилища реализуют порты, объявленные в
  `application/ports.py`.
- `domain.py` не импортирует другие модули проекта.
- Клиент модели — порт `LlmClient`. `main.py` подключает
  `RoutingLlmClient`: один HTTP-адаптер chat completions, заголовки
  выбираются по `LlmProfile.api_kind`. UI показывает это перечисление
  и не импортирует классы драйверов.

## 5. Карта файлов: за что каждый отвечает

Ниже — по каждому файлу: назначение, что он импортирует, кому он нужен
и на какие файлы он не должен влиять.

### 5.1. `main.py`

- **Назначение:** composition root. Создаёт `FileSessionCatalog`,
  `EncryptedJournalRepository`, `ApplicationService` с `driver_factory`,
  `MainWindow`. Запускает Qt event loop.
- **Импортирует:** `application`, `drivers`, `storage`, `ui`.
- **Используется:** только как точка входа `python main.py`.
- **Меняется, когда:** добавляются новые провайдеры, новые реализации
  хранилищ, новые окна верхнего уровня. Бизнес-логики здесь быть не должно.

### 5.2. `domain.py`

- **Назначение:** доменные модели (`SessionConfig`, `SessionInfo`,
  `CommandRequest`, `OutputEvent`, `TranscriptEvent`, `CommandResult`),
  перечисления (`ProviderType`, `SessionStatus`, `ExecutionIdentityType`,
  `StreamType`, `EventType`), типизированные исключения
  (`JournalAuthError`, `JournalCorruptedError`, ...), функции
  `new_session_id()`, `new_command_id()`, `new_event_id()`.
  У `OutputEvent` и `TranscriptEvent` есть поле `persist`: `False` означает
  живой кадр терминала, который подписчикам отдаётся, но в журнал не пишется.
  Номер `sequence` при этом не расходуется.
- **Импортирует:** только стандартную библиотеку.
- **Используется:** всеми модулями проекта.
- **Меняется, когда:** нужно добавить новое поле в модель события,
  новый тип события, новый провайдер, новые статусы. Меняется осторожно —
  затрагивает и UI, и драйверы, и хранилище.

### 5.3. `application/ports.py`

- **Назначение:** только протоколы и типы-алиасы:
  - `SessionDriver` — открыть, отправить, писать в PTY текущей команды,
    менять размер PTY, закрыть, приём событий, автодополнение.
  - `SessionCatalog` — список сессий.
  - `JournalRepository` — создание, разблокировка, дозапись, чтение.
  - `DriverFactory`, `EventCallback`.
- **Импортирует:** `domain.py`, стандартную библиотеку.
- **Используется:** `application/service.py`, `drivers/*`, `storage/*`.
- **Меняется, когда:** меняется контракт между слоями. Правки здесь
  требуют проверки всех реализаций (драйверов и хранилищ).

### 5.4. `application/service.py`

- **Назначение:** класс `ApplicationService`. Реализует сценарии:
  создание/открытие/закрытие сессий, отправку команды, чтение истории,
  подписку UI на события, многосессионную маршрутизацию событий
  драйверов в журнал и подписчиков.
- **Импортирует:** `domain.py`, `application/ports.py`.
- **Используется:** `ui/main_window.py`, `main.py`.
- **Меняется, когда:** появляется новый сценарий (например, «экспорт
  журнала», «переименование сессии»), меняется логика очередей команд
  или подписки. Не должен знать про PySide6, subprocess и конкретные
  хранилища.

### 5.5. `drivers/factory.py`

- **Назначение:** `driver_factory(provider) -> SessionDriver`.
  Единственное место, где решается, какой класс драйвера создать
  для конкретного `ProviderType`.
- **Импортирует:** `domain.py`, `application/ports.py`, конкретные
  драйверы (`drivers/cmd.py`, `drivers/ssh.py`).
- **Используется:** `main.py` (передаётся в `ApplicationService`).
- **Меняется, когда:** добавляется новый драйвер (одна новая ветка).

### 5.6. `drivers/cmd.py`

- **Назначение:** `CmdSessionDriver`. Запускает команды в ConPTY
  (`cmd.exe /c` временного `.bat`), держит stdin открытым, следит за `cwd`,
  эмитит живые кадры PTY (`persist=False`) и в конце текст основного экрана.
- **Импортирует:** `domain.py`, `screen_log.py`, `pywinpty`, стандартную библиотеку.
- **Используется:** `drivers/factory.py`.
- **Меняется, когда:** нужно поменять поведение CMD-сессии
  (например, отслеживать переменные окружения, добавить повышение прав).

`drivers/ssh.py` делает то же для удалённой команды: `get_pty`, stdin не
закрывается, `write_input` / `resize_pty`. Каталог после команды читается
отдельным `pwd` в файл, а не маркером в самом PTY. `screen_log.py` — общий
лист без Qt: копит основной экран и не отдаёт в снимок alternate screen.

### 5.7. `storage/catalog.py`

- **Назначение:** `FileSessionCatalog` — JSON-файл с несекретными
  метаданными сессий.
- **Импортирует:** `domain.py`, стандартную библиотеку.
- **Используется:** `main.py` (передаётся в `ApplicationService`).
- **Меняется, когда:** меняется формат хранения метаданных, добавляются
  новые несекретные поля (`host`, `port`, `CredentialRef` для SSH).

### 5.8. `storage/journal.py`

- **Назначение:** `EncryptedJournalRepository`. Формат файла:
  заголовок (magic/version/iterations/salt) + последовательность
  записей, каждая — `uint32 length` + `nonce(12)` + `ciphertext`.
  AAD = заголовок + `uint64 sequence`. Ключ — PBKDF2-HMAC-SHA256.
- **Импортирует:** `domain.py`, `cryptography`, стандартную библиотеку.
- **Используется:** `main.py` (передаётся в `ApplicationService`).
- **Меняется, когда:** меняется формат журнала, добавляется смена
  пароля, ротация ключей, квотирование размера.

### 5.9. `ui/styles.py`

- **Назначение:** `build_mono_font()`, `build_text_formats()`,
  `TextFormats`, константа `STYLESHEET` (QSS).
- **Импортирует:** PySide6.
- **Используется:** `ui/main_window.py`, `ui/command_card.py`.
- **Меняется, когда:** меняется тема, цвета, шрифты.

### 5.10. `ui/command_card.py`

- **Назначение:** `CommandCard` — виджет карточки одной команды и её
  вывода. Пока команда идёт, показывает `TerminalView` и отдаёт клавиши
  наружу. После завершения снова показывает статичный текст.
- **Импортирует:** PySide6, `ui/terminal_view.py`.
- **Используется:** `ui/main_window.py`.
- **Меняется, когда:** меняется вид карточки, добавляется подсветка
  синтаксиса, кнопка «выполнить снова» и т.п.

### 5.11. `ui/dialogs.py`

- **Назначение:** `CreateSessionDialog` (имя + пароль + подтверждение),
  `UnlockSessionDialog` (пароль для разблокировки).
- **Импортирует:** PySide6.
- **Используется:** `ui/main_window.py`.
- **Меняется, когда:** появляются новые поля в форме создания сессии
  (SSH-параметры, выбор провайдера), новые диалоги.

### 5.12. `ui/main_window.py`

- **Назначение:** `MainWindow`. Список сессий слева, чат и поле ввода
  справа. Подписывается на события `ApplicationService`, держит отдельную
  ленту на каждую открытую сессию (живой `nano` не сбрасывается при
  переключении), вызывает сценарии. Tab в нижнем поле дополняет строку,
  второй Tab показывает список вариантов. Пока команда выполняется, фокус
  в карточке; `write_input` и `resize` уходят в сервис.
- **Импортирует:** PySide6, `domain.py`, `application/service.py`,
  `ui/command_card.py`, `ui/dialogs.py`, `ui/styles.py`.
  `screen_log.py` импортирует только `ui/terminal_view.py`.
- **Используется:** `main.py`.
- **Меняется, когда:** меняется компоновка окна, добавляется панель
  SSH-подключения, изменяется поведение при переключении сессий.
  Не должен импортировать `drivers/`, `storage/`, `cryptography`.


## 6. Контракты данных

### 6.1. `TranscriptEvent` (запись истории/журнала)

Поля: `event_id`, `session_id`, `sequence`, `event_type`, `timestamp`,
`command_id?`, `stream_type?`, `payload`, `return_code?`, `status?`,
`persist`.

`sequence` нумеруется от 0 в рамках сессии и только для событий с
`persist=True`. `ApplicationService` присваивает `event_id` и `sequence`
перед записью в журнал. События с `persist=False` подписчикам уходят,
в файл не пишутся и номер не занимают. В JSON журнала поля `persist` нет.

### 6.2. Поток событий

1. UI вызывает `ApplicationService.send_command(session_id, text)`.
2. Драйвер сессии отправляет `COMMAND_SENT`.
3. Драйвер читает PTY и шлёт `OUTPUT_CHUNK` с `persist=False`.
   UI рисует их в карточке и шлёт клавиши через `write_input`.
4. Перед завершением драйвер шлёт один `OUTPUT_CHUNK` с `persist=True`:
   текст основного экрана. Alternate screen (`nano`, `less`) в него не входит.
5. При завершении — `COMMAND_FINISHED` с кодом возврата. Фокус возвращается
   в нижнее поле.
6. При ошибке запуска — `ERROR`.
7. При открытии/закрытии сессии — `SESSION_STATUS`.

`ApplicationService` для `persist=True` проставляет `event_id`/`sequence`,
пишет в журнал и уведомляет подписчиков. Ошибка записи в журнал эмитится
отдельным событием `ERROR`, чтобы UI показал проблему.

### 6.3. Разделение секретов

- Пароль журнала передаётся только в `create_session`/`open_session`
  и не попадает ни в `SessionConfig`, ни в каталог, ни в драйвер.
- SSH-учётные данные (этап 2.2) планируется передавать через
  `CredentialRef`; сам секрет в `SessionConfig` не хранится.
- Журнал и каталог не содержат секретов в открытом виде.


## 7. Куда идти за изменениями

Этот раздел — путеводитель для правок. Если нужная фича не описана —
ориентируйтесь по правилам из раздела 3 (зависимости) и разделу 5
(карта файлов).

### 7.1. Изменить внешний вид (тема, цвета, шрифт)

Файлы: `ui/styles.py` (QSS + форматы), при необходимости
`ui/command_card.py` (структура карточки).

### 7.2. Изменить поведение поля ввода (горячие клавиши, история команд, Tab)

Файл: `ui/main_window.py` (методы `eventFilter`, `_navigate_history`,
`_on_submit`, `_on_tab_complete`). Список вариантов в журнал не пишется.
Клавиши внутри живой карточки — это ввод процесса, не автодополнение:
`ui/terminal_view.py`.

### 7.3. Изменить форму создания сессии (добавить поле)

Файлы:
- `ui/dialogs.py` — добавить поле в `CreateSessionDialog`;
- `ui/main_window.py` — передать новое значение в сценарий;
- `application/service.py` — принять параметр в `create_session`;
- `domain.py` — расширить `SessionConfig`, если поле относится к сессии;
- `storage/catalog.py` — если поле надо хранить в каталоге.

### 7.4. Добавить новый провайдер (SSH, PowerShell, WSL)

Файлы:
- `domain.py` — добавить значение в `ProviderType`;
- `drivers/<new>.py` — новый драйвер, реализующий `SessionDriver`;

- `ui/dialogs.py` — поля, специфичные для провайдера;

- `application/service.py` — если у провайдера другой жизненный цикл.

Менять `ui/command_card.py`, `application/ports.py`,
`storage/journal.py` **не нужно**.

### 7.5. Изменить формат журнала

Файл: `storage/journal.py`. Правки локализованы здесь.
`domain.py` и `ui/` не меняются.
Увеличивайте `VERSION` и реализуйте миграцию/поддержку старых версий.

### 7.6. Добавить новое поле в событие истории

Файлы:
- `domain.py` — поле в `OutputEvent`/`TranscriptEvent`;
- `drivers/cmd.py` — заполнение при создании `OutputEvent`;
- `storage/journal.py` — сериализация в JSON при дозаписи/чтении;
- `ui/main_window.py` — отображение (если нужно).

### 7.7. Добавить новый сценарий в приложение

Файлы:
- `application/service.py` — метод-сценарий;
- `ui/main_window.py` — вызов из UI;

### 7.8. Добавить новый способ хранения журнала

- Новый класс в `storage/<name>.py`, реализующий `JournalRepository`.
- В `main.py` подменить конкретную реализацию.
- `application/service.py`, `ui/` не меняются.

### 7.9. Добавить новое окно/диалог верхнего уровня

- Новый файл в `ui/`, ре-экспорт из `ui/__init__.py` при необходимости.
- Открытие — из `ui/main_window.py` или `main.py`.

### 7.10. Изменить логику выполнения команд

## 9. Ручные проверки

### 9.1. Базовое поведение CMD

- `echo Hello` — stdout, код возврата 0.
- `dir` — длинный вывод, корректная кодировка.
- `ping -n 5 127.0.0.1` — окно не блокируется, статус RUNNING.
- `nonexistent_command` — текст ошибки в карточке, ненулевой код возврата.
  В PTY stdout и stderr слиты в один поток.
- `echo Привет` — русские буквы не ломаются.
- `cd ..` → `dir` — директория сменилась.
- `cd /d D:\` — переход на другой диск.
- Up/Down в поле ввода листают команды этой сессии из журнала,
  сверху вниз: стрелка вверх — более ранняя, вниз возвращает черновик,
  который был в поле до листания. В многострочной команде стрелки
  сначала двигают курсор и листают историю только с края текста.
  У каждой сессии свой текст поля
  и своя позиция в истории; переключение сессий их не смешивает.
- Heredoc вроде `cat <<EOF` и следующих строк остаётся в поле, пока
  закрывающая метка не введена. Enter после неё отправляет всё сразу.
- Tab дописывает единственный вариант или общий префикс. Второй Tab
  показывает список под полем, в чат он не попадает.
- Повторный Enter во время выполнения — вторая команда не уходит.
  Ctrl+C в блоке выполняющейся команды прерывает её.

### 9.1.1. Интерактив в блоке ответа (SSH)

- `nano файл` — экран редактора внутри карточки этой команды, нижнее
  поле погашено. Ctrl+O / Ctrl+X работают. После выхода фокус снова
  в нижнем поле, в истории остаётся строка команды.
- `less файл` — листание стрелками и пробелом в той же карточке, `q`
  возвращает нижнее поле.
- `ssh guest` или `virsh console` — весь гостевой сеанс в одной карточке,
  пока эта команда не завершится. Команды внутри гостя отдельными блоками
  не становятся.
- Переключение на другую сессию и обратно не гасит открытый `nano`.

### 9.2. Сессии и журнал

- Форма создания: пустое имя, пустой пароль, несовпадающие пароли —
  отклоняются с понятным сообщением.
- Созданная сессия активна, ввод работает.
- Закрытие сессии очищает чат, запись в списке сохраняется.
- В списке видно, активна сессия или нет: «активна» у открытой,
  «не активна» у закрытой. Текущая помечена ▶.
- «Удалить сессию» спрашивает подтверждение и стирает журнал.
  Пока в сессии выполняется команда, удаление отклоняется.
- Двойной клик по закрытой сессии → диалог пароля.
  - Неверный пароль → «Неверный пароль».
  - Верный пароль → журнал разблокирован, история восстановлена.
- После перезапуска приложения список сессий сохранился, история
  восстанавливается по паролю.
- Файл журнала бинарный, читаемого текста нет.
- Ошибка записи журнала (файл только для чтения) показывается
  в чате как «Ошибка записи журнала: …».

### 9.3. Многосессионность

- Две сессии. Активная помечена `▶`, вторая — `●`.
- Длинная команда в одной, параллельная работа во второй.
- Переключение туда-обратно не смешивает истории.
- Ввод блокируется только в той сессии, где выполняется команда.
- Закрытие активной сессии с открытой второй — активируется вторая.
- Закрытие приложения со всеми открытыми сессиями — все драйверы
  гасятся, файлы журналов остаются на диске.


## 10. Контроль архитектурных контрактов

- `ui/*` не импортирует `drivers/*` и `storage/*`, не использует
  `cryptography`. Живой экран берёт `screen_log.py`, это лист без Qt
  и без процессов; драйверы импортируют его же для снимка журнала.
- `application/*` не импортирует PySide6, `subprocess`, `cryptography`
  и конкретные реализации хранилищ.
- `domain.py` не импортирует другие модули проекта.
- `drivers/cmd.py` не знает про журнал и пароль журнала.
- `storage/*` не импортирует UI и драйверы.
- `main.py` — единственное место создания конкретных реализаций.
- Замена хранилища не требует правок в UI и драйверах.
- Добавление SSH-драйвера не требует правок в модели истории
  и сценариях отправки команд.

  через системный механизм Windows.
- Подтверждение и ввод учётных данных выполняет сама Windows.
- Если используется IPC, канал ограничить сессией и локальным
  пользователем.

### 11.3. Не входит в перечисленные этапы

- функции ИИ;
- анализ журналов;
- автоматическое выполнение команд.


## 12. Как использовать эту документацию

Если нужно добавить или изменить функциональность:

1. Найдите подходящий раздел в **§7 «Куда идти за изменениями»**.
2. Если сценарий не описан — определите слой по **§3 «Архитектура»**
   и по карте файлов в **§5**.
3. Убедитесь, что правки не нарушают правила из **§10**.
4. Проверьте результат по **§9**.
5. Если добавляется новый провайдер, новый формат журнала или новая
   модель события — затрагивается `domain.py`, поэтому проверьте
   все реализации портов.

Для типовых задач достаточно показать помощнику:

- **UI-правка:** `ui/styles.py`, `ui/command_card.py`,
  `ui/main_window.py`, `ui/dialogs.py` (что применимо).
- **Драйвер:** `domain.py`, `application/ports.py`, `drivers/factory.py`,
  `drivers/cmd.py` (и новый `drivers/<name>.py`).
- **Хранилище:** `domain.py`, `application/ports.py`,
  `storage/catalog.py`, `storage/journal.py`.
- **Сценарий приложения:** `domain.py`, `application/ports.py`,
  `application/service.py` + точка вызова в `ui/main_window.py`.
- **Всё вместе:** `main.py` как образец связывания.
