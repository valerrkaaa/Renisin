# Двойная лицензия: файлы, CLA Assistant и проверка перед внешним PR

Репозиторий на GitHub этой инструкцией не настраивается. Шаги ниже выполняет правообладатель вручную, когда решит включить проверку.

Ветка по умолчанию: `master`.
Проверка CLA Assistant в статусе коммита называется `license/cla`.


## Какие файлы уже лежат в репозитории

| Файл | Назначение |
| --- | --- |
| `LICENSE` | Уведомление: AGPL-3.0-only или отдельная коммерческая лицензия. Выражение SPDX `AGPL-3.0-only OR LicenseRef-Commercial`. |
| `LICENSES/AGPL-3.0-only.txt` | Дословный текст GNU AGPL-3.0. Его не редактировать. |
| `LICENSES/LicenseRef-Commercial.txt` | Идентификатор коммерческой лицензии. Сам по себе права не даёт. |
| `CLA.md` | Broad CLA для контрибьюторов. |
| `CONTRIBUTING.md` | PR без подписи CLA не принимается. Шаблон заголовка. |
| `docs/copyright-header.txt` | Строка авторского права для исходных файлов. |


## CLA Assistant

CLA Assistant (https://cla-assistant.io) комментирует pull request и ставит статус `license/cla`. Текст CLA он берёт из GitHub Gist, а не из файла в ветке: так подпись привязана к конкретной редакции. Список подписавших хранится у CLA Assistant; из интерфейса его можно выгрузить в CSV.

1. Откройте https://gist.github.com под учётной записью владельца репозитория.
2. Создайте публичный gist. Имя файла: `CLA.md`. Вставьте текущий текст `CLA.md` из репозитория без правок.
3. При желании добавьте в тот же gist второй файл с именем `metadata` (без расширения). CLA Assistant построит форму перед подписью:

```json
{
  "name": {
    "title": "Full Name",
    "type": "string",
    "githubKey": "name",
    "required": true
  },
  "email": {
    "title": "E-Mail",
    "type": "string",
    "githubKey": "email",
    "required": true
  },
  "category": {
    "title": "How do you sign?",
    "type": {
      "enum": [
        "I am signing on behalf of myself.",
        "I am signing on behalf of my employer."
      ]
    },
    "required": true
  },
  "agreement": {
    "title": "I have read and agree to the CLA",
    "type": "boolean",
    "required": true
  }
}
```

4. Откройте gist и скопируйте raw-URL файла `CLA.md`. Адрес содержит `raw` или `githubusercontent.com` и заканчивается на `/CLA.md`.
5. Войдите на https://cla-assistant.io той же учётной записью GitHub и разрешите приложению доступ к репозиторию `Renisin`.
6. Нажмите Configure CLA, выберите репозиторий и вставьте raw-URL gist в поле документа CLA. Сохраните.
7. В поле исключений укажите `*[bot]`, чтобы боты вроде Dependabot не блокировали свои PR. Учётную запись правообладателя туда добавляйте только если он не будет подписывать CLA на собственные PR. Чужие аккаунты не исключайте.
8. Откройте пробный pull request с другой учётной записи. На PR должен появиться комментарий CLA Assistant, а в проверках — `license/cla` со статусом pending или failed.
9. Подпишите CLA по ссылке из комментария. Статус `license/cla` должен стать success, а комментарий — обновиться. Второй PR той же учётной записи должен получить success сразу.
10. После этого включайте обязательную проверку. Имя `license/cla` появляется в списке проверок только после того, как CLA Assistant хотя бы раз выставил статус.


## Обязательная проверка в защите ветки

Без этого шага красный `license/cla` остаётся предупреждением: GitHub всё ещё позволит влить PR.

Классическое правило, Settings → Branches → Add branch protection rule:

1. Branch name pattern: `master`.
2. Включите Require a pull request before merging, если прямые push в `master` тоже не должны обходить CLA. Прямой push проверку CLA не запускает.
3. Включите Require status checks to pass before merging.
4. В списке проверок отметьте `license/cla`. Если имени нет, вернитесь к пробному PR из шага 8 и обновите страницу правила.
5. Сохраните правило.
6. Повторите пробный PR без подписи и убедитесь, что кнопка merge недоступна, пока `license/cla` не зелёный.

Тот же запрет через ruleset: Settings → Rules → New branch ruleset, enforcement Active, цель — ветка `master`, правило Require status checks to pass, проверка `license/cla`.

На бесплатном личном аккаунте обязательные проверки для приватного репозитория могут быть недоступны. Для публичного репозитория защита ветки доступна. Пока проверки нельзя сделать обязательной, внешний PR не вливается вручную, пока статус `license/cla` не success.

Изменение gist меняет редакцию CLA. Участники подписывают её заново на следующем PR. После правки `CLA.md` в репозитории обновите gist тем же текстом.


## Что проверить перед первым внешним PR

- В `LICENSE`, `CLA.md` и `LICENSES/LicenseRef-Commercial.txt` указано юридическое имя правообладателя, а не только имя из git. Сейчас везде стоит «Валерий».
- Контакт коммерческой лицензии `valerrkaaa3@gmail.com` актуален, и с него отвечают на запросы.
- `LICENSES/AGPL-3.0-only.txt` совпадает с https://www.gnu.org/licenses/agpl-3.0.txt и не правился.
- Текст gist и текст `CLA.md` в `master` совпадают.
- CLA прочитан юристом. Это шаблон под dual licensing, а не заключение.
- В исходных файлах, которые готовы к публикации, стоит заголовок из `docs/copyright-header.txt`.
- Пробный PR без подписи не вливается. Пробный PR с подписью получает зелёный `license/cla`.
- В исключениях CLA Assistant нет посторонних пользователей.
- В `master` нет чужих коммитов, принятых до подписи CLA. Уже принятый чужой код эта схема задним числом не лицензирует.
- Перед публикацией решено, что правообладатель готов соблюдать AGPL-3.0 для тех, кто выбрал открытую лицензию, включая передачу исходного кода по разделу 13, если изменённая программа доступна по сети.
